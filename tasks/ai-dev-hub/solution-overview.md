# AI Dev Hub 完整方案总览

## 1. 一句话定义

AI Dev Hub 是一个部署在腾讯云服务器上的 AI 开发任务中台，用来统一管理多个 AI 编程工具的任务、上下文、执行记录、交接文档和后续接力。

它不是新的 IDE，而是 AI 编程工具的“项目经理”和“调度台”。

## 2. 当前要解决的问题

用户当前有多种 AI 开发能力：

- Cursor / Cursor CLI。
- Codex Plus / Codex CLI。
- Claude Code。
- 公司 API 额度。

这些工具能力不同，额度不同，使用入口不同。真实痛点不是缺少工具，而是：

1. 不知道什么时候该用哪个工具。
2. 切换工具时上下文断裂。
3. AI 做过什么没有沉淀成项目资产。
4. 上班公司电脑、下班个人电脑，开发现场不统一。
5. 担心某个工具额度用完后，其他工具无法无缝接手。

## 3. 目标状态

理想状态：

```text
公司电脑 / 个人电脑
        ↓
访问同一个腾讯云 AI Dev Hub
        ↓
查看同一个任务列表、上下文、日志和交接文档
        ↓
调用 Cursor CLI 执行
        ↓
未来可切到 Codex CLI / Claude Code 继续执行
```

最终目标：

> 用户可以换电脑、换 AI 工具，但任务现场不丢。

## 4. 产品定位

AI Dev Hub 的定位不是：

- 不是代码编辑器。
- 不是完整 IDE。
- 不是替代 Cursor。
- 不是一开始就做多模型平台。
- 不是公网 SaaS。

AI Dev Hub 的定位是：

- AI 任务管理器。
- AI 上下文管理器。
- AI 工具调度器。
- AI 执行日志中心。
- AI 交接文档生成器。
- AI 工作流记忆系统。

## 5. 第一版产品边界

第一版只解决一个核心问题：

> 让 Cursor CLI 的执行过程可管理、可记录、可交接。

第一版必须有：

1. 项目注册。
2. 任务创建。
3. 上下文生成。
4. Cursor CLI 调用。
5. 执行日志保存。
6. Git diff 读取。
7. Handoff 生成。
8. Review Prompt 生成。
9. 多设备访问同一个任务状态。

第一版暂不做：

1. 不做完整 IDE。
2. 不做在线代码编辑器。
3. 不做多用户权限系统。
4. 不做复杂 agent 编排。
5. 不做自动部署。
6. 不做自动 merge。
7. 不做所有 AI 工具同时接入。

## 6. 推荐落地路径

### 阶段 1：CLI 原型

先实现最小命令：

```bash
aihub init
aihub project add
aihub task create
aihub context
aihub run --agent cursor
aihub handoff
aihub review
aihub done
```

目标是跑通“创建任务 → 生成上下文 → 调用 Cursor CLI → 保存日志 → 生成交接”的闭环。

### 阶段 2：腾讯云私有部署

把 CLI、项目工作区、Cursor CLI、SQLite 数据库和日志都部署到腾讯云。

公司电脑和个人电脑只作为访问终端。

### 阶段 3：本地 Web UI

提供一个只在安全网络内访问的 Web 页面：

- 任务列表。
- 当前任务。
- 执行按钮。
- 日志查看。
- Diff 查看。
- Handoff 查看。

### 阶段 4：记忆和偏好

逐步记录：

- 用户偏好。
- 项目规则。
- 技术决策。
- 工具使用效果。

所有记忆必须可查看、可编辑、可删除。

### 阶段 5：多工具接力

在 Cursor CLI 稳定后，再接入：

- Codex CLI：review、测试生成、第二实现。
- Claude Code：复杂架构分析、重构方案。
- 公司 API：总结、归档、批处理。

## 7. 成功判断标准

MVP 成功不是“AI 自动写多少代码”，而是：

1. 用户换电脑后能继续同一个任务。
2. Cursor CLI 执行过程能被记录。
3. 每次执行后能生成明确 handoff。
4. 下一个 AI 工具能基于 handoff 接手。
5. 用户不需要反复解释项目背景。

北极星指标：

> 跨工具接续时，用户需要重复解释的次数。

目标是把这个次数降到接近 0。
