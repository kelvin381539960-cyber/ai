# AI Dev Hub 方案评审记录

日期：2026-05-28

## 1. 总体结论

结论：有条件通过，可以进入 CLI 原型实现，但必须先收窄 MVP。

当前方案已经完成关键纠偏：不再绑定 Cursor CLI、Codex CLI、Claude Code 或任何单一工具，而是采用能力模型与 Agent Adapter 扩展架构。这个方向是正确的。

但当前文档覆盖面较广，如果直接按完整 MVP 实现，第一版容易膨胀成平台工程。建议把实现切成更小的 V0，只验证核心闭环。

## 2. 通过项

### 2.1 产品定位清楚

方案已经明确 AI Dev Hub 不是 IDE，而是 AI 开发任务中台。

核心定位成立：

```text
任务管理 + 上下文管理 + 能力路由 + 执行记录 + Handoff 接力
```

### 2.2 抽象方向正确

当前抽象为：

```text
Task → Required Capabilities → Candidate Agents → Selected Adapter → Run Result → Handoff
```

这个抽象比“直接接某个 CLI 工具”更合理，能避免后续工具变化导致工作流重建。

### 2.3 不绑定具体工具

文档已经明确：

- 具体工具通过 Adapter 接入。
- Cursor / Codex / Claude / 公司 API 都只是可选执行器。
- 第一版不应硬编码任何具体工具。

该方向通过。

### 2.4 `.ai/` 工作区设计合理

`.ai/` 作为 AI 可读工作区是正确的。

它解决了：

- 跨工具接力。
- 多电脑接续。
- 过程沉淀。
- 任务状态可读。

### 2.5 安全边界基本正确

已明确：

- 不自动 push。
- 不自动 merge。
- 不自动 deploy。
- 不直接公网暴露 UI。
- 密钥不进 Git。
- 日志默认不进 Git。

方向通过。

## 3. 主要风险

## P0：MVP 仍然偏大

当前 MVP 包含：

- 项目管理。
- 任务管理。
- Agent 管理。
- 能力模型。
- Adapter Runtime。
- SQLite。
- `.ai/` 工作区。
- Handoff。
- Review Prompt。
- 安全策略。
- 后续 Web UI。

这些内容都合理，但不能在第一轮同时实现。

建议将实现切成 V0 / V1：

### V0 只做闭环验证

```text
init → agent add → task create → context → run manual/cli → handoff
```

V0 不做：

- HTTP Adapter。
- Web UI。
- Preferences。
- Metrics。
- Cost。
- 多项目复杂管理。
- 多 run 并发。
- 自动 review agent 调用。

### V1 再做增强

```text
review prompt → run complete → sqlite 完整化 → 安全策略增强 → UI
```

## P0：Generic CLI Adapter 的安全边界需要更硬

Generic CLI Adapter 是关键能力，但它天然有风险，因为它可以执行任意命令。

当前方案依赖：

- prompt 约束。
- 执行前后 git status。
- diff 检查。
- 人工确认。

这还不够。

建议 V0 增加硬规则：

1. 默认只允许在 Git 仓库内执行。
2. 默认禁止在 `main` / `master` 分支执行，除非 `--allow-main`。
3. 默认不允许自动 commit / push / merge / deploy。
4. 默认不允许修改敏感文件：
   - `.env`
   - `*.pem`
   - `*.key`
   - `id_rsa`
   - `config/secret*`
5. 执行后如果检测到敏感文件变更，必须标记 run 为 high_risk。

## P1：数据源职责需要进一步明确

当前同时有 SQLite 和 `.ai/` 文件系统。

这是合理的，但需要明确：

```text
数据库是结构化状态源
.ai 是 AI 可读上下文源
```

建议规则：

- task 状态以数据库为准。
- task 内容同时写入 `.ai/TASKS/<task_id>.md`。
- handoff 内容以 `.ai/HANDOFF.md` 为准，数据库存索引。
- run 日志以文件为准，数据库存路径和摘要。
- Agent 本地配置以 `.ai/AGENTS.yaml` 和 `.ai/AGENTS.local.yaml` 为准，数据库可以缓存。

V0 可以先不做复杂同步机制，只实现单向写入。

## P1：Manual Adapter 生命周期还需要纳入 CLI

`adapter-runtime.md` 提到了：

```bash
aihub run complete <run_id>
```

但 `cli-spec.md` 的优先级列表里没有把它列入必做。

Manual Adapter 是 V0 的关键兜底能力，所以必须补入 V0。

建议 V0 必须支持：

```bash
aihub run complete <run_id>
```

用途：

- 用户把外部 AI 工具结果粘贴回来。
- 系统关闭 manual_pending run。
- 系统基于结果生成 handoff。

## P1：能力模型需要先收敛

当前能力列表较完整，但 V0 不应全部实现。

建议 V0 只保留 6 个能力：

```text
plan
code_edit
shell_run
test_run
review
summarize
```

其他能力保留在文档中，但实现时先不做复杂路由。

## P1：Agent 配置需要避免泄漏密钥

当前文档已说明密钥不进 Git，但 Agent 配置还需要更明确的规则。

建议：

- `AGENTS.yaml` 可以进 Git，但不能含密钥。
- `AGENTS.local.yaml` 不进 Git，可保存本地路径和私有 endpoint。
- token 只能通过环境变量引用。
- 执行日志必须脱敏常见 secret pattern。

## P1：Review Prompt 不应进入默认执行链

Review Prompt 很重要，但不应阻塞 V0。

建议：

- V0 可以生成 review prompt。
- V0 不自动调用 review agent。
- Review Agent 调用放到 V1。

## P2：Web UI 需要延后

UI 文档可以保留，但实现必须延后。

建议：

- V0：CLI only。
- V1：本地 Web UI 只读查看。
- V2：Web UI 支持触发执行。

## 4. 建议的 V0 实现范围

V0 目标：验证最小可用闭环。

### V0 必须实现

```text
aihub init
aihub agent add
aihub agent list
aihub agent test
aihub task create
aihub task show
aihub context
aihub run --agent <agent_id>
aihub run --capability <capability>
aihub run complete <run_id>
aihub handoff
```

### V0 必须支持的 Adapter

```text
Manual Adapter
Generic CLI Adapter
```

### V0 暂不支持

```text
HTTP Adapter
Web UI
多用户
权限系统
成本统计
偏好记忆
多 run 并发
自动 review agent
自动 commit / push / merge / deploy
```

## 5. V0 成功标准

V0 完成后必须能演示：

1. 初始化 `.ai/` 工作区。
2. 注册一个 manual agent。
3. 注册一个 generic cli agent。
4. 创建一个带 required_capabilities 的任务。
5. 生成上下文。
6. 用 manual agent 生成可复制 prompt。
7. 用 `run complete` 粘贴外部结果。
8. 用 generic cli agent 执行一次简单命令。
9. 保存 run 日志。
10. 生成 handoff。
11. 下一个工具能基于 handoff 接手。

## 6. 是否可以进入实现

可以，但按 V0 进入，不按完整 MVP 进入。

推荐实现策略：

```text
先做文件系统 + 最小 SQLite
先做 Manual Adapter
再做 Generic CLI Adapter
最后做 handoff
```

不要一开始做：

- Web UI。
- HTTP Adapter。
- 成本系统。
- 复杂路由。
- 自动化多 agent 编排。
