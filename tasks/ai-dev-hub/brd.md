# AI Work Hub MVP BRD

## 1. 项目名称

暂定：AI Work Hub

原代号：AI Dev Hub

## 2. 项目背景

产品经理、运营、技术型 PM 和个人开发者正在同时使用多个 AI 工具完成工作。

常见问题：

- 任务状态分散在多个 AI 对话中。
- 调研、PRD、运营方案、评审、总结等流程无法沉淀。
- 每次都要重新写 prompt。
- 不同 AI 工具输出无法统一管理。
- 同一任务缺少持续上下文。
- 多电脑工作现场不统一。
- AI 输出和任务资料缺少统一沉淀。

需要一个私有部署的 AI 工作流任务中台，帮助用户围绕“任务”持续推进工作，并沉淀资料、过程和输出。

## 3. 产品定位

AI Work Hub 的定位是：

```text
产品经理 / 运营的 AI 工作台
```

更正式定义：

```text
面向产品、运营、技术型 PM 和个人开发者的 AI 工作流任务中台。
```

核心价值：

```text
以任务为中心，管理资料、助手、流程、输出和交接，让 AI 工作可以持续推进。
```

它不是：

- 不是 IDE。
- 不是代码编辑器。
- 不是单一 AI 工具客户端。
- 不是 Agent 市场。
- 不是复杂 Workflow 平台。
- 不是多 Agent 自动编排平台。
- 不是公网 SaaS。

Agent、Workflow、Run、Handoff、Adapter 都是底层能力组件，不是用户第一入口。

## 4. 目标用户

优先用户：

```text
产品经理 / 运营 / 技术型 PM / 个人开发者
```

典型特征：

- 同时使用多个 AI 工具。
- 经常做调研、PRD、评审、总结、运营方案。
- 希望从任务类型直接开始，而不是先配置工具。
- 希望把任务资料和 AI 输出沉淀下来。
- 希望把重复流程沉淀为任务流程。
- 希望把常用角色沉淀为助手。
- 希望同一任务持续积累上下文和结论。
- 少数场景需要接入开发 CLI 或代码 Agent。

## 5. 业务目标

MVP 目标：

```text
让用户从任务类型开始，添加资料，使用推荐助手和流程，持续生成输出并沉淀任务结论。
```

核心业务目标：

- 用户无需先理解 Agent / Workflow 就能开始任务。
- 多任务可管理。
- 任务资料可沉淀。
- 多助手可复用。
- 多任务流程可复用。
- 每次 AI 输出可记录。
- 每个任务可生成结论和交接。
- 换工具、换电脑后任务现场不丢。

## 6. 用户主路径

MVP 主路径：

```text
选择任务类型
→ 填写目标
→ 添加资料
→ 系统推荐默认助手和任务流程
→ 开始执行
→ 查看输出
→ 继续优化 / 找其他助手评审
→ 生成最终结论 / 交接说明
```

首页第一问题：

```text
你想完成什么？
```

默认入口：

- 做需求调研。
- 写 PRD。
- 做竞品分析。
- 做运营方案。
- 整理会议纪要。
- 做评审。
- 做数据复盘。
- 技术追问。
- 自定义任务。

## 7. 核心业务对象

### 7.1 Workspace

用户工作空间。

一个 Workspace 下可以有多个 Project / Space。

### 7.2 Project / Space

业务空间或项目。

例如：

- 某产品版本。
- 某运营活动。
- 某调研专题。
- 某代码项目。

### 7.3 Task

AI 工作任务。

一个 Task 可以：

- 有任务类型。
- 有任务资料。
- 有默认助手。
- 运行任务流程。
- 生成多个输出。
- 生成多个执行记录。
- 生成最终结论或交接说明。

### 7.4 Material / Source

任务资料。

支持：

- 文本。
- 链接。
- 文件。
- 截图。
- 会议纪要。
- 用户反馈。
- 竞品资料。
- 历史结论。
- 外部 AI 输出。

### 7.5 Assistant / Agent

可复用 AI 助手。

UI 中称为“助手”。

底层仍可叫 Agent。

默认助手对应底层 Primary Agent。

### 7.6 Workflow

任务流程。

UI 中称为“流程”或“任务流程”。

MVP 只支持线性步骤。

### 7.7 Run

执行记录。

Run 是底层记录，不作为用户主入口。

### 7.8 Output

输出结果。

类型包括：

- 调研结论。
- PRD 草稿。
- 竞品分析报告。
- 运营方案。
- 会议纪要。
- 评审意见。
- 下一步行动项。
- 交接说明。

### 7.9 Handoff

交接说明。

Handoff 是 Output 的一种。

## 8. MVP 核心业务能力

### 8.1 Workspace / Project 管理

用户可以创建或选择 Workspace / Project。

### 8.2 任务类型入口

用户从任务类型开始创建任务。

任务类型：

- research。
- prd。
- competitive_analysis。
- ops_plan。
- data_analysis。
- meeting_summary。
- review。
- tech_review。
- dev_task。
- custom。

### 8.3 任务资料管理

每个任务可以添加多条资料。

资料可以被任务流程和助手引用。

### 8.4 默认助手

创建任务时系统推荐默认助手。

用户可以：

- 使用推荐助手。
- 更换默认助手。
- 临时找其他助手看看。

### 8.5 助手管理

用户可以管理多个助手。

MVP 推荐助手模板：

- 调研助手。
- PRD 助手。
- 竞品分析助手。
- 运营方案助手。
- 数据分析助手。
- 会议纪要助手。
- 评审助手。
- 技术追问助手。
- 代码助手。

### 8.6 任务流程管理

用户可以使用或创建任务流程。

MVP 推荐流程模板：

- 需求调研流程。
- PRD 生成流程。
- 竞品分析流程。
- 运营活动流程。
- 评审流程。
- 会议纪要流程。
- 交接总结流程。
- 开发前准备流程。

### 8.7 输出结果管理

用户可以查看任务产生的输出。

输出可以被继续优化，也可以作为资料进入下一轮任务。

### 8.8 资料范围

底层 Context Mode 在 UI 中叫“资料范围”。

选项：

- 简洁：只使用任务目标和最新结论。
- 标准：使用任务目标、任务资料和最近输出。
- 完整：使用全部资料、历史记录和相关文件。

默认：标准。

## 9. MVP UI 范围

主导航建议：

```text
首页
任务
资料
助手
流程
输出
设置
```

页面范围：

- 首页。
- 任务列表页。
- 任务创建页。
- 任务详情页。
- 资料管理区。
- 助手管理页。
- 流程管理页。
- 输出页。
- 设置页。

Run / Handoff 不作为一级主导航。

Run 显示为任务详情页中的执行记录。

Handoff 显示为输出的一种。

## 10. MVP 不做范围

MVP 明确不做：

- 完整 IDE。
- 在线代码编辑器。
- 复杂 DAG Workflow。
- Workflow 条件分支。
- Workflow 并行步骤。
- 多 Agent 自动智能编排。
- 任务内频繁自动切换 Agent。
- 自动 commit。
- 自动 push。
- 自动 merge。
- 自动 deploy。
- 成本统计。
- 偏好记忆。
- 多用户权限。
- 公网 SaaS。
- 绑定具体 AI 工具。
- ChatGPT Action。
- MCP Server。

开发相关能力作为高级能力保留，不作为默认主流程。

## 11. 扩展性要求

MVP 必须满足：

- 一个 Workspace 支持多个 Project / Space。
- 一个 Project / Space 支持多个 Task。
- 一个 Task 支持多个 Material。
- 一个 Task 支持一个默认助手。
- 一个 Task 支持多个其他助手调用。
- 一个 Task 支持多个流程运行记录。
- 一个 Task 支持多个 Output。
- 一个 Assistant 可被多个 Task 复用。
- 一个 Workflow 可被多个 Task 复用。
- 后续可扩展条件分支和 DAG，但 MVP 不实现。
- 后续可扩展 HTTP Adapter，但 MVP 不实现。
- 后续可暴露 REST API / ChatGPT Action / MCP。

## 12. 核心原则

### 12.1 任务优先

用户从任务开始，不从工具配置开始。

### 12.2 资料优先

产品/运营任务的输入是资料，资料必须成为核心对象。

### 12.3 输出优先

用户关心输出结果，Run 和 Handoff 是底层记录。

### 12.4 默认助手持续推进

一个任务默认由一个默认助手持续推进。

用户可以随时找其他助手看看，也可以更换默认助手。

### 12.5 产品/运营优先

默认场景优先服务产品、运营、技术型 PM 的日常 AI 工作流。

开发任务是重要扩展场景，但不是唯一主线。

## 13. MVP 典型场景

### 13.1 产品需求调研

用户选择“做需求调研”，填写问题，添加资料，系统推荐调研助手和需求调研流程，最终生成调研结论。

### 13.2 PRD 生成

用户选择“写 PRD”，添加需求背景、用户反馈、业务目标，系统生成 PRD 草稿，并可调用评审助手优化。

### 13.3 运营活动策划

用户选择“做运营方案”，添加活动目标和历史数据，系统生成活动方案和执行清单。

### 13.4 竞品分析

用户添加竞品链接、截图、资料，系统生成竞品分析报告和跟进建议。

### 13.5 会议纪要

用户粘贴会议记录，系统生成纪要、结论和行动项。

### 13.6 技术追问

产品经理可以把技术方案作为资料，调用技术追问助手生成问题清单和评审意见。

## 14. 成功标准

MVP 完成后必须能演示：

1. 用户从首页选择任务类型开始。
2. 用户可以创建任务并添加资料。
3. 系统自动推荐默认助手和流程。
4. 用户可以运行流程。
5. 用户可以查看输出结果。
6. 用户可以找其他助手评审。
7. 用户可以更换默认助手。
8. 系统保存执行记录。
9. 系统生成最终结论或交接说明。
10. 用户不需要先理解 Agent / Workflow 才能开始。

## 15. 业务指标

MVP 关注：

- Task 创建数量。
- Material 添加数量。
- Output 生成数量。
- Workflow 运行次数。
- Assistant 使用次数。
- 用户从创建任务到生成第一个输出的时间。
- 用户重复解释任务背景次数下降。

## 16. 关键风险

### 风险 1：产品变成工具配置台

控制：

- 首页从任务类型开始。
- Agent / Workflow 作为配置项，不作为用户第一入口。

### 风险 2：误做成开发者工具

控制：

- 默认场景围绕调研、PRD、运营、会议、评审。
- Git、Diff、CLI 降级为高级能力。

### 风险 3：范围膨胀

控制：

- Workflow 只做线性步骤。
- 不做 DAG。
- 不做多 Agent 自动编排。

### 风险 4：Token 成本增加

控制：

- 引入资料范围。
- 默认不传全量历史。
- 优先传摘要、任务目标、关键结论。
